## The rule that governs every file

> **Production build only.**

Every item in every layer file is judged against a **production build** — `NODE_ENV=production`,
`nest build`, `vite build`, EAS release profile — running against a **production-shaped
database**. Nothing here is satisfied by a dev server, a watch build, a seeded demo tenant, a
staging image, or a passing unit test on its own.

## Status legend

| Symbol | Meaning | Who may set it |
| --- | --- | --- |
| `[ ]` | **Not started** — no code, or code exists but nobody has looked. | anyone |
| `[~]` | **Code exists, UNVERIFIED** — an implementation is present in the repo but has not been proven against a production build. **This is not progress.** | anyone |
| `[x]` | **Verified in a production build** — proven, with evidence in the Evidence column or a linked commit/CI run. | only after evidence exists |
| `[-]` | **Deliberately out of scope for v1** — must carry a written reason and a follow-up ticket. | Kannan only |

## The evidence rule

> **A box may only be ticked when someone can point at proof that a stranger could re-run.**

**Acceptable evidence**

- a command plus its pasted output (`pnpm --filter api test`, `curl -i …`, `docker compose … up`)
- a CI run URL
- an `EXPLAIN (ANALYZE, BUFFERS)` plan with the measured number written down
- a screenshot of the **production build** — not the dev server — showing the behaviour
- a migration file plus the rollback that was actually executed against a copy

**Not acceptable**

- "it looks right"
- "the code is there"
- a passing unit test with a mocked Prisma client (see [J.2.1](checklists/10-TESTING.md))
- an audit report generated by a tool or an agent

> ⚠️ **Repo-root audit and readiness reports** — `PAGE-ANALYSIS-AUDIT-REPORT.md`,
> `POC_V6_ORIGINAL_DATA_AND_AUDIT_REPORT.md`, `STAGING-READINESS-REPORT.md`,
> `PRODUCTION-READINESS.md`, `FRONTEND-PRODUCTION-READINESS-QUESTIONNAIRE.md`,
> `ENGINEERING-CHECKLIST.md`, `DB-SCHEMA-CHECKLIST.md` — are **historical** and contain claims
> that do not match the code. **Never tick a box in any layer file on their authority.**
> Re-verify against the code and a running production build, every time.

## Rules for maintaining these files

1. **Never delete a row.** If an item stops being relevant, mark it `[-]` with the reason.
2. **Never tick in bulk.** One box, one piece of evidence.
3. **Re-open on regression.** If a verified item breaks, set it back to `[ ]` and log it in
   [O.3 Regression log](checklists/15-GO-LIVE.md).
4. **Update `Last reviewed`** in the layer file *and* here whenever you touch either.
5. **New feature ⇒ new rows** in A, C, D, and N — not a new document.
6. **One owner per layer.** Fill in the **Layer owner** field at the top of each file.
